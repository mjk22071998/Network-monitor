### C. Step-by-Step API Review (All 7 Groups Approved)
A thorough, patient group-by-group review of [api_contracts_specification.md](file:///d:/FullStackProjects/Network%20monitor/api_contracts_specification.md) was completed:

1. **Group 1: Authentication & User Administration**:
   * `POST /api/v1/auth/login`: Returns numeric `role_id` and `site_id` (clean, unbloated).
   * `GET /api/v1/auth/me`: Returns `user_id`, `username`, `role_id`, `site_id`, `is_active`, `created_at`.
   * `PUT /api/v1/auth/password`: Authenticated self-password update with current password validation.
   * `GET /api/v1/users`: Returns string descriptors (`role`, `site_name`) for direct tabular display.
   * `POST /api/v1/users` & `PUT /api/v1/users/{id}`: Accept and return numeric `role_id` and `site_id`.
   * **Zero Self-Registration**: No public sign-up; all operators provisioned by `NETWORK_ADMIN`.

2. **Group 2: Operational Enclave Site & Group Hierarchy**:
   * Single-site enclave locked (`site_id = 1`) via `GET / PUT /api/v1/site`.
   * `GET /api/v1/groups`: Nested hierarchy using **`children: [...]`** attribute; leaf groups return an empty list `[]`.
   * `DELETE /api/v1/groups/{id}`: Protected fallback reassigns orphaned devices and subgroups to `group_id = 1` (Unassigned Group).

3. **Group 3: Device Inventory CRUD**:
   * Strict 1:1 database schema mapping: all 10 columns (`display_name`, `primary_ip`, `mac_address`, `type_id`, `group_id`, `parent_device_id`, `vendor`, `model`, `zone`, `is_monitored`).
   * MAC address is the immutable natural hardware key (rejects change with `422 DEVICE_MAC_IMMUTABLE`).
   * Orphan-safe deletion: deleting a parent switch clears `parent_device_id` on children (`SET NULL`), preventing accidental cascades.

4. **Group 4: Topology, Telemetry & Polling Configuration**:
   * Topology tree renders horizontal backbone + vertical 2-branch parallel endpoint columns under Access Switches.
   * `GET / PUT /api/v1/monitoring/config` (**Option 1**): Configures global ICMP reachability intervals (5s default) and host health intervals (30s default), backed by `monitoring_config` singleton table.
   * **Physical Spatial Layouts (`/api/v1/layouts/...`)**: Formally tagged as **`[DEFERRED: FUTURE DEVELOPMENT / MILESTONE 2]`** across all documents.

5. **Group 5: Operational Diagnostics & Subnet Discovery**:
   * `POST /api/v1/discovery/scan`: Asynchronous ICMP ping sweep and SNMP bridge interrogation.
   * `GET /api/v1/discovery/scan/{scan_id}`: Polls progress percentage and newly discovered assets.
   * `PUT /api/v1/devices/{id}/maintenance`: Toggles `is_monitored = false`, turns node slate-gray (`UNKNOWN`), suppresses downstream alerts, logs to audit trail.

6. **Group 6: Bulk File Ingestion Pipeline (CSV / SQLite)**:
   * **`[PROVISIONAL: SUBJECT TO REVISION DURING DEVELOPMENT]`**: Tagged across all docs.
   * Architecture defined: Persistent database staging (`import_batches`, `staged_devices`), surviving server reboots and browser closures; automated pre-resolution; inline cell editing; partial commit (`commit_valid_only: true`); Admin-only commit gatekeeper. Structure will be finalized during dev with real production fixtures.

7. **Group 7: Security Audit Trail Contracts**:
   * `GET /api/v1/audit/logs`: `NETWORK_ADMIN` exclusively. Paginated append-only query with action code, user, and ISO 8601 date range filters.

## 2. Definitive Architectural Decisions Locked In

| Architectural Area | Locked Decision | Specification Reference |
| :--- | :--- | :--- |
| **Single Source of Truth**| All 5 master specification documents are absolute authority. Undocumented changes are halted immediately. | PRD § Directives, UI Guidelines § 12 |
| **System Scope** | Single operational site per installation (`site_id = 1`) via `/api/v1/site`. Schema supports future federation. | PRD v2.1 § FR-4.1 / SRS v2.1 § 5.2 |
| **Security Roles** | Exactly 3 roles: `NETWORK_ADMIN` (1), `NETWORK_ENGINEER` (2), `IT_SUPPORT` (3). Zero self-registration. | SRS v2.1 § 5.7 / Schema Spec § 6 |

| **Relational Schema** | **PostgreSQL 16+ / 17+ / 18+** Level 3 Normalized (3NF) with Declarative Range-Partitioning on `reachability_samples` & `health_samples`. PL/pgSQL immutability triggers on `audit_logs`. | Schema Spec v2.1 § 4, SRS v2.1 § 5.8 |
| **Telemetry Nullability** | Strict "Never Zero for Missing Data" (N/A) rule. `latency_us` and `ntp_offset_us` are `NULL` on timeout/unsupported. | Schema Spec v2.1 § 4 |
| **Cascading Suppression**| Switch failure triggers downstream suppression (`status_id = 3 (SUPPRESSED)`, `is_suppressed = 1`), halting synthetic pings. | SRS v2.1 § 5.5 |
| **Polling Engine Config**| Managed via `monitoring_config` singleton table through `GET / PUT /api/v1/monitoring/config`. | Schema Spec v2.1 § 3 / API Spec § 7 |
| **Implementation Tech Stack** | **Backend**: C# (.NET 8 LTS) ASP.NET Core Web API + Entity Framework Core (EF Core) + Npgsql.<br/>**Frontend**: Vue 3 + Vite + TypeScript + Tailwind CSS + Cytoscape.js + Apache ECharts.<br/>**Database**: PostgreSQL 16/17/18.<br/>**Runtime**: ASP.NET Core serves `/api/v1/...` and `/dist` assets from port `8443` (or `5000`). | SRS v2.2 § 8, Arch Spec § 2 |
| **Memory Efficiency Architecture** | **Working Ceiling**: **60 MB – 100 MB** for both backend RSS and frontend JS heap.<br/>**Backend**: Asynchronous stream spooling + Npgsql binary import + EF Core batching.<br/>**Frontend**: `markRaw()` on Cytoscape.js and Apache ECharts instances, `shallowRef()` for telemetry batches, strict 50-row pagination. | Arch Spec § 5, PRD v2.2 § NFR-2 |
| **Spatial Floorplans** | **[DEFERRED: FUTURE DEVELOPMENT / MILESTONE 2]** Physical layout decoupled from Phase 1 MVP runtime. | Schema Spec v2.1 § 3, API Spec § 10 |
| **Bulk File Ingestion** | **[PROVISIONAL: SUBJECT TO REVISION DURING DEVELOPMENT]** Persistent database staging tables (`import_batches`, `staged_devices`) surviving reboots; atomic commit. Structure to be finalized with live data in dev. | Schema Spec v2.1 § 5, 7, API Spec § 9 |
| **UI Theme & Canvas** | Cyber-tactical theme (`#050811`, `#070b16`), Cytoscape.js multi-layer canvas, horizontal backbone + vertical 2-branch endpoint layout under access switches. | UI Guidelines § 2, 6, Arch Spec § 2.2 |
| **Table Pagination** | Standardized tactical footer across all registries (`[ 25 \| 50 \| 100 \| 250 ]`, range counters, page pills). | UI Guidelines § 8.3 |
| **Form Attributes** | Strict 1:1 database schema mapping: all 10 `devices` columns (`display_name`, `primary_ip`, `mac`, `type_id`, `group_id`, `parent_device_id`, `vendor`, `model`, `zone`, `is_monitored`). | UI Guidelines § 9.1 |
| **Prototype Role** | Prototype is binding *skeleton & item-placement reference only*. Visual UI/UX styling to be overhauled during production build. | UI Guidelines § 12 |
